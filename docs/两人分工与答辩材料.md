# 两人小组分工、测试与答辩材料

> 适用于《专业课程设计》— 基于 ECDHE 的前向保密聊天工具
> 使用方式：
> 1. **第一节（分工）** 交给自己看，用于明确边界；
> 2. **第二节（测试）与第三节（演示脚本）** 两份报告的"测试章节"可直接粘贴，只需替换"本人负责部分"的小节；
> 3. **第四节（论文素材）** 供"局限性 / 展望"章节使用。

# 一、详细分工方案

## 1.1 分工原则

1. **按"关注点"分，而不是按"文件"分**：一人主攻密码协议，一人主攻网络/容错/存储/测试工程；但**两边都碰得到对方的代码**（A 写会话状态机的调用路径，B 写加密封装的调用方式），避免"某人只写纯算法、对系统一无所知"。
2. **每人都有代码 + 测试 + 文档**：见 1.4 / 1.5 / 1.6 的对应关系。
3. **公共章节完全一致、个人章节互不重叠**：两份报告都能独立成篇，合起来又是一套完整系统。

## 1.2 成员 A —— 密码协议方向

| 文件 | 关键函数 / 类 | 负责内容 |
|---|---|---|
| `Common/crypto_utils.h` | `x25519_generate` / `x25519_shared` / `x25519_public_raw`<br>`hkdf` / `sha256` / `hmac_sha256`<br>`aead_encrypt` / `aead_decrypt`<br>`ed25519_generate` / `sign` / `verify` / `*_pem`<br>`wipe` | OpenSSL EVP 封装；密钥长度校验；敏感数据清零；静态库下改用内存 BIO 规避 `applink` |
| `Common/secure_session.h` | `BuildInit` / `HandleInit` / `HandleResp` / `HandleConfirm`<br>`Derive` / `TranscriptHash` / `ComputeSas`<br>`BuildRecord` / `Seal` / `Open`<br>`ApplyRatchet` | 三报文握手；签名覆盖范围；HKDF 域分离；Finished 校验；消息级棘轮；**DH 棘轮**；安全码派生 |
| `Common/protocol.h` | 帧字段布局、`HS_*_BASE/LEN`、`make_aad` | 协议常量与 AAD 构造（收发方/会话号/序号绑定） |
| `ClientGUI/ClientGUI.cpp`（会话部分） | `PeerSession`、`LockedStartHandshake`、`LockedSendChat`、`LockedFlushOutbox`、`HandleInit/Resp/Confirm/Data`、`CheckPin` | 会话状态机、握手调用路径、待发队列、TOFU 指纹校验 |
| `Tests/crypto_selftest.cpp` | 第 1–6 组断言（共 **28 项**） | 签名、X25519、HKDF、GCM、棘轮、协议级完整握手 + DH 轮换 |

**核心难点**：签名与验签的输入必须严格一致；密钥"使用"与"清零"的顺序；棘轮推进与失败回滚。

## 1.3 成员 B —— 网络、容错、存储与测试工程

| 文件 | 关键函数 / 类 | 负责内容 |
|---|---|---|
| `Server/server.cpp` | `SendFrame` / `SendPayload` / `SendSystem`<br>`HandleClient` / 心跳巡检线程 | 连接管理、按 ID 路由、**每连接写锁**、帧长上限、PING/PONG、60 s 空闲回收、整行日志 |
| `ClientGUI/ClientGUI.cpp`（网络与工程部分） | `NetworkThread`、`MakeFrame` / `SendRaw`、`WM_TIMER`（心跳/重连）<br>`SaveChatMsg` / `LoadAllChats` / `SavePin` / `LoadPins`<br>`DpapiProtect` / `DpapiUnprotect`、`--profile` / `--dump`<br>`LayoutControls`、`RefreshSessionList`、`RefreshChatView`、`ApplyChatEvent`、`OnSendClicked`、`WindowProc`、`WinMain` | 阻塞读循环、心跳 5 s / 超时 15 s、自动重连 2 s、加密持久化、DPAPI、多档案、导出、界面与布局 |
| `Tools/mitm_relay.cpp` | `Route` / `ForwardData` / `FlushPending` | 中间人攻击工具（冒充服务器、终止两端握手、解密转发） |
| `Tools/mitm_demo.ps1`、`Tools/smoke_test.ps1` | 窗口自动化、断言、截图 | 端到端自动化测试与演示脚本 |
| `CMakeLists.txt`、`Tools/make_report_docx.py` | 构建与报告生成 | CMake 4 的 Boost CONFIG 模式、`/utf-8`、链接 `crypt32` |

**核心难点**：多线程写同一 socket 的帧交错；锁序；跨线程 UI 更新；跨进程读取控件不可靠。

## 1.4 工作量对比

| 维度 | 成员 A | 成员 B |
|---|---|---|
| 主要代码量 | 约 1000 行（crypto_utils 400 + secure_session 450 + 协议 140） | 约 1900 行（server 230 + 客户端网络/存储/UI 约 900 + 工具 700） |
| 难度类型 | 算法与协议正确性（错了就握手失败或安全性归零） | 并发、异常路径、平台差异（错了就偶发/难复现） |
| 可复用资产 | `SecureSession` 被客户端与攻击工具共用 | 测试脚本、MITM 工具、构建体系 |
| 论文分量 | 理论与安全证明、协议设计 | 工程实现、测试方法与数据 |

结论：**代码行数 B 略多，理论与排错深度 A 略深**，总体均衡。

## 2.4 弱网测试

**方法**：使用 Clumsy 或 NetLimiter 对本机回环注入延迟与丢包，参数建议"延迟 200 ms / 丢包 5%"。

**观察与结论**：

| 场景 | 表现 | 说明 |
|---|---|---|
| 仅增加延迟 | 消息延迟到达，顺序与内容正确 | TCP 有序 + 序号单调，延迟不影响正确性 |
| 出现丢包 | 会话因序号断档被判定"失步/重放"，随后重置并需要重新握手 | **这是当前设计的已知限制**：协议不支持乱序与丢帧恢复（详见 4.1） |

> 答辩时可主动说明：这不是 bug，而是"在 TCP 之上只处理有序可靠流"的设计取舍；若要支持乱序，需要引入按消息 DH 头的双棘轮与 skipped-key 缓存。

## 2.5 安全专项测试

| 编号 | 测试项 | 方法 | 预期结果 | 实际结果 |
|---|---|---|---|---|
| S-01 | 中间人攻击 | `Tools\mitm_demo.ps1` | 中间人打印出明文；两端安全码不同 | 一致（见下） |
| S-02 | 前向保密 | 记录密文 → 删除 `identity.pem` → 重启 | 历史密文无法解密 | 一致 |
| S-03 | 后向恢复 | 连发 > 8 条触发 DH 轮换 | 旧链密钥无法解密轮换后的消息 | 自测断言成立 |
| S-04 | 重放攻击 | 将同一 `DATA` 帧重复投递 | 第二次被"序号失步或重放"拒绝 | 一致（该分支已在调试中实际触发） |
| S-05 | 指纹变化阻断 | 先经 MITM 建立信任，再连真实服务器 | 提示"对端身份公钥与已记录的指纹不一致，已阻止" | 已实现（`CheckPin` 分支） |
| S-06 | 服务器不可解密 | 查看服务器日志 | 只有字节数，无任何明文 | 一致 |

**S-01 实测输出**：

```
[MITM] 已冒充用户 2 接受用户 1 的握手
[MITM] 已冒充用户 1 向用户 2 发起握手
[MITM] 欺骗成功：用户 1 与用户 2 都显示“加密会话已建立”
[MITM] 但两端的安全码不同：用户 1 看到 629420，用户 2 看到 795209
[截获] 1 -> 2 明文: card-password-is-123456
[抓包]   密文 39 字节，前 16 字节 fdb3776657d7af05ca5e9bc670fd210e
```

**结论**：首次接触且中间人在场时，ECDHE 无法自动阻止劫持（信息论限制）；但两端安全码必然不同，**核对一次即可发现**。这与 Signal / WhatsApp 的安全模型一致。

## 2.6 测试结论

1. 28 项密码学与协议断言全部通过，涵盖签名、密钥交换、KDF、AEAD、两种棘轮与完整握手流程。
2. 端到端自动化测试覆盖"握手 → 收发 → 落盘 → 导出 → 棘轮"全链路，5 项断言全部通过。
3. 边界与异常路径（离线、自发、空收件人、超长消息、断线重连、畸形帧）均给出明确提示，未出现崩溃或卡死。
4. 安全专项验证了"服务器不可解密""前向保密""后向恢复""重放拒绝""MITM 可被发现"五项结论。
5. 已知不足：不支持乱序/丢帧恢复；弱网丢包会导致会话重置。

## 3.1 演示步骤（10 分钟主线，两人交替）

> 原则：**不要一边点一边解释代码**。每一段只讲一句"这是什么"，再讲一句"为什么值得看"。
> 顺序按"能看见安全属性"排列：先证明服务器看不到 → 再证明能发现中间人 → 最后证明出问题也能救回来。

| # | 时间 | 操作 | 台词（照着说） | 讲 |

## 3.2 五个亮点，每个 30 秒（可插在任意节点）

被问"你们有什么亮点"时不要展开讲全部，**挑一句 + 一个证据**：

| 亮点 | 一句话 | 证据（当场给对方看什么） |
|---|---|---|
| 服务器零密钥 | 中继彻底不可信，攻破也拿不到明文 | 服务器控制台只有字节数；MITM 反证"只有主动劫持才能解密" |
| 协议代码可复用 | 客户端和攻击工具跑的是**同一份** `SecureSession` | `Tools/mitm_relay.cpp` 直接 `#include "secure_session.h"` |
| 三层密钥演进 | 会话（ECDHE）→ 消息（链棘轮）→ 周期（DH 棘轮），前向保密 + 后向恢复都有 | 第 9 条消息触发 REKEY；CryptoTest 第 5、6 组 |
| 帧头进 AAD | 篡改、重放、换收件人全部失效 | 加密时 AAD = `ver‖type‖sid‖seq‖发送方‖接收方` |
| 可验证身份 | 签名防篡改、安全码防替换、TOFU 防二次劫持 | 两端安全码对比；指纹变化直接阻断 |

## 3.3 现场问题库（26 条，按被问概率排序）

### A. 协议与密码学（成员 A 主答）

| 问题 | 回答要点 |
|---|---|
| ECDHE 为什么能提供前向保密？ | 会话密钥只由**临时**私钥算出的 Z 派生，与长期身份私钥无关；临时私钥用完即毁，事后拿到身份私钥也重算不出 Z |
| 和 TLS 1.3 有什么区别？ | 结构同构（ECDHE + HKDF + AEAD）。区别：① 认证用 Ed25519 + 安全码，不是证书链；② 记录层额外做了消息级棘轮（TLS 只有会话级） |
| 为什么不用 OpenSSL 的 TLS 库？ | 课程目标是搞清握手内部；套 TLS 就只剩调 API。我们把 TLS 1.3 的关键步骤自己实现了一遍 |
| HKDF 的 salt 为什么用 nonceA‖nonceB？ | 让每次握手的中间值都不同；即使 Z 因某种原因重复，派生出的密钥也不会相同（抗跨会话密钥复用） |
| 签名和 Finished 有什么区别？ | 签名证明"我是谁"（身份），Finished 证明"我们算出了同一把钥匙"（密钥确认），两者不可互相替代 |
| 安全码为什么 6 位？够吗？ | 10⁶ 空间，人工 30 秒能核对完；中间人无法让两端一致（transcript 不同），只能赌概率；需要更强可换 12 词 |
| 中间人能不能伪造安全码？ | 不能。安全码是两端**各自**由 transcript 算的，攻击者改了握手内容就签名失效，不改则两端 transcript 必然不同 |
| 后向恢复靠什么实现？ | 每 8 条消息轮换：新 X25519 密钥对 → 用旧链加密 REKEY → 双方更新根密钥 → 销毁旧私钥。泄露的密钥最多覆盖一个轮换周期 |
| 为什么消息密钥要每条一换？ | 单条消息密钥泄露不牵连其他消息；代价是每条多 3 次 HKDF，实测可忽略 |
| 密钥怎么保证不被 swap 出去？ | 目前只做了 `OPENSSL_cleanse` 覆盖（进程内），没有锁内存页（`VirtualLock`），这是可改进项 |

### B. 攻击与边界（A 主答）

| 问题 | 回答要点 |
|---|---|
| 中间人为什么能成功？ | **首次接触**时身份公钥只是"自我介绍"，没有第三方背书。这是 TOFU 模型的固有边界，Signal 也一样 |
| 那你们的安全码有什么意义？ | 把"不可检测的劫持"变成"可检测的异常"。而且第二次连接有指纹固定（TOFU），指纹变了直接阻断 |
| 服务器被完全控制会怎样？ | 拿不到明文、拿不到历史密钥；但可以拒绝服务、可以看到"谁在何时发给谁"的元数据 |
| 为什么不做元数据保护？ | 中继必须知道目标 ID 才能转发。要隐藏需要消息填充 + 批量混洗 + 匿名路由，超出课程规模 |
| 重放 / 乱序 / 丢帧怎么办？ | 重放被序号单调校验拒绝；乱序和丢帧目前会**重置会话**（已知限制，标注在 6.5） |
| 量子计算来了怎么办？ | X25519 / Ed25519 都不是后量子。工程上可换混合密钥交换（X25519 + ML-KEM），协议结构不用改 |
| 随机数从哪来？ | OpenSSL `RAND_bytes`，走操作系统 CSPRNG |
| 你们自己写的密码学可信吗？ | 算法不自己写，全部用 OpenSSL EVP；我们写的是**协议组合**，并用 28 项断言 + 攻击工具验证 |

### C. 网络与并发（成员 B 主答）

| 问题 | 回答要点 |
|---|---|
| 为什么用 TCP？ | 聊天是低频强序场景；棘轮也依赖严格有序，UDP 要自己实现重传、排序、跳跃密钥缓存 |
| 多线程写同一 socket 怎么不串帧？ | 每连接一把 `write_mu`，**长度与载荷在同一临界区**写出；否则两帧字节交错，对端无法还原边界 |
| 全局锁会不会成瓶颈？ | 锁内只做一次 map 查找，**阻塞写放在锁外**；慢客户端只占自己的写锁 |
| 一个慢客户端会拖垮服务吗？ | 不会。这是当初把"锁内阻塞写"改掉的原因 |
| 心跳参数怎么定的？ | 5 秒发一次 PING、15 秒没 PONG 判死、2 秒重试一次。15 秒 ≈ 3 个周期，兼顾发现速度与误判 |
| 为什么帧长上限 1 MiB？ | 长度字段是攻击面：不设上限，一个 `0xFFFFFFFF` 就能让服务器申请 4 GB |
| 客户端崩溃后 ID 会不会被占用？ | 服务器每 10 秒巡检，60 秒无活动就断开并回收 ID |

### D. 存储与身份（B 主答）

| 问题 | 回答要点 |
|---|---|
| 私钥怎么保护的？ | Windows DPAPI（`CryptProtectData`），以当前账户为密钥；文件拷到别的账户/机器都解不开 |
| 换机器会怎样？ | 身份重新生成 → 历史无法解密。这是**预期行为**，报告里写明了 |
| 为什么不放数据库？ | 单机课程项目，按"身份指纹 / 对端 ID"分文件最简单；加密后放进 DB 也只是一坨 blob，不增加安全性 |
| 聊天记录被替换会怎样？ | AAD 绑定了对端 ID，张冠李戴地拼接会解密失败 |
| 目录名为什么用身份指纹而不是用户 ID？ | 服务器 ID 是临时的（重启就变），身份密钥才是持久的；这样重启、换 ID 后历史与指纹固定仍有效 |

### E. 测试与验证（B 主答，A 补安全测试意图）

| 问题 | 回答要点 |

| 28 项断言覆盖什么？ | 6 组：Ed25519、X25519、HKDF、AES-GCM、消息级棘轮、协议级 DH 棘轮（完整握手 + 20 条消息 + 自动轮换） |

# 四、论文素材

## 4.1 项目局限性（如实说明，答辩加分）

| # | 局限 | 具体表现 | 影响 | 可缓解方式 |
|---|---|---|---|---|
| 1 | **不支持乱序与丢帧恢复** | 序号严格单调，检测到断档即作废会话 | 弱网丢包后需重新握手，期间的待发消息会丢弃 | 双棘轮（每条消息携带 DH 头）+ skipped-key 缓存 |
| 2 | **身份信任依赖人工核对** | 首次接触只能 TOFU，指纹绑定临时 ID | 首次握手被劫持时无法自动发现 | PKI/证书、扫码核对、预置公钥 |
| 3 | **元数据未保护** | 服务器可见通信关系、消息长度与时序 | 可做流量分析 | 定长填充、批量发送、中继网络 |
| 4 | **功能范围有限** | 无离线消息、群聊、文件传输；单条上限 64 KB | 实用性受限 | 服务器密文缓存、Sender Keys、分片 |
| 5 | **本地保护有边界** | DPAPI 只防跨账户/跨机器；同账户进程仍可读 | 本机被同一用户攻破时无效 | 口令派生密钥、硬件密钥 |
| 6 | **报错粒度较粗** | 网络异常统一提示"断开，正在重连" | 排障信息不足 | 分级日志与错误码 |
| 7 | **无速率限制与审计** | 服务器不做限流 | 易被刷 | 令牌桶、连接数上限 |
| 8 | **无形式化验证** | 安全性依赖人工推理与测试 | 难以证明无逻辑漏洞 | ProVerif / Tamarin 建模 |

## 4.2 未来扩展方向

| # | 方向 | 具体做法 | 预期收益 |
|---|---|---|---|
| 1 | **完整双棘轮** | 每条消息携带 `DH公钥 + n`，接收端缓存 skipped keys | 支持乱序，且后向恢复粒度到"每条消息" |
| 2 | **KeyUpdate** | 按时间（如每 10 分钟）触发 REKEY | 长会话安全性更平滑 |
| 3 | **离线消息** | 服务器暂存密文，上线补投（服务器仍不可解密） | 可用性大幅提升 |
| 4 | **群聊** | Sender Keys：每个成员分发群密钥，复用现有 ECDHE 通道 | 从 1:1 扩展到群组 |
| 5 | **文件传输** | 分片 + 复用记录层，带完整性校验 | 实用性 |
| 6 | **元数据保护** | 长度填充到固定档位、批量发送 | 抗流量分析 |
| 7 | **私钥备份** | 口令加密导出 + 助记词校验 | 换机不丢身份 |
| 8 | **形式化验证** | ProVerif 建模握手，验证 secrecy 与 agreement | 论文级证据 |
| 9 | **性能优化** | Asio strand / 异步 I/O、连接池、压测数据 | 支撑更多并发 |
| 10 | **界面完善** | 消息搜索、失败重发、托盘通知 | 体验 |
